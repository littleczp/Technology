# 游戏开发手册

在确认《游戏设计》大纲后，我们进行游戏制作前的最后一步，制定游戏开发手册（PRD）。

{% hint style="info" %}
一份完整的AI游戏开发手册应该包含哪些内容/结构？

一、设计层（Design Layer）

1. 游戏概述（类型、平台、核心体验锚点）
2. 非目标（明确砍掉、推迟或禁止实现的功能）
3. 核心循环
4. 术语表（统一核心系统命名、变量缩写、状态枚举）

二、协议层（Contract Layer）

1. 技术栈与环境基准（游戏引擎）
2. 目录结构与命名规范
3. 场景与资源契约（缺失资源时的占位机制）
4. 静态数据：数据表 Schema 与存档格式（Json/ScriptableObject/二进制及版本迁移）
5. 动态数据：事件总线与生命周期时序（全局 Event 定义、Update 执行优先级）
6. 模块边界与依赖方向（单向依赖规则、禁止的反模式/防循环依赖约定）

三、执行层（Execution Layer）

1. 任务切分与上下文管理（单次 Prompt 的任务粒度标准，避免超出上下文窗口）
2. 验证与调试规范（单元测试、可视化 Gizmos、作弊/调试指令要求）
3. 工作流与重构流程（读文档 -> 出技术方案 -> 编码 -> 人工/自动化复核）
4. AI 协作约定（System Prompt 片段、禁止输出未完成的代码伪代码片段、强制类型检查）
5. 架构决策记录（ADR）（记录重大设计变更及“为什么不采取另一种做法”）

# 这份手册的用途
手册是本项目的**唯一事实来源（SSOT）**，唯一用途是帮助设计各个系统，切分成若干独立开发包，
分发给**互相看不到对方上下文的 AI agent** 各自实现。因此：
- 它可寻址、可裁剪、单一归属的事实库
- 每个被拆分的系统尽量遵循**可冷启动、可独立验收、可局部返工**

# 内容边界
允许写：接口签名与语义、数据结构与约束、依赖方向、状态机、伪代码、算法、时序
禁止写：框架 API 调用、类与继承设计、具体库选型与版本、性能优化手法

# 开发手册基础结构

## 第 0 层：AGENTS.md 和 CLAUDE.md（仓库根目录）
**严格限量**，因为它是每个 agent 都必读的唯一全局文件。只放：
一句话项目定位 / 文档地图 / ID 命名规范 / 依赖方向铁律 / 开发红线 / Definition of Done。
不许放玩法内容。

## 术语表（独立于三层，全局共用）
一词一义，标注归属系统，禁止同义词并存。

## 设计层
1. 游戏概述
2. 非目标：明确不做什么
3. 核心循环
4. **系统划分**

## 协议层（契约层）
1. 技术栈（只到"选型约束与理由"，不到具体版本与用法）
2. 目录结构与命名规范
3. 数据表 schema 与存档格式
4. 模块边界与依赖方向
5. **全局事件/命令/查询总表**（系统之间唯一允许的交互方式）

## 执行层
1. 工作流（含讨论顺序、变更流程）
2. 验证方式
3. AI 协作约定
4. 决策记录（ADR）

# 系统划分要求
**划分标准：按状态所有权，不按 UI 页面或功能名词。**
每一份状态数据有且仅有一个系统是 owner，其他系统只能通过命令/事件间接影响它。
一个系统一次性整理、一次确认、统一落档，再进入下一个系统。

**参考的系统总表：
| 系统ID | 名称 | 一句话职责 | 所属层 | 拥有的状态 | 上游依赖 | 被谁依赖 | 规模(S/M/L) |

# 核心原则
1. 一次只讨论一个系统，不遗留待确认问题。
2. 不必顺从我的观点，做出独立分析和建议；我的方案有问题请直接指出。
3. 可以给出类似的游戏是如何设计的（2~3个），以向我提供思路。
5. 你可以并通过提问的方式与我交互以确认细节。
6. 可后置的实现细节，在构建对应模块时再展开。

# 输出
不用着急给出文档，只有与我确认没有要解决的问题后，在得到我的"确认"回复后输出或修改文档。

# 每次输出前的自检
1. 本次讨论的内容能否放到系统实现时讨论，如果"可以"则后续再讨论。
2. 本次讨论的设计是否展开成了过重的处理，如果"是"则应该简化或者考虑删除。
