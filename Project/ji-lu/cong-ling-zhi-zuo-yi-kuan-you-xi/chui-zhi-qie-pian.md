# 这份手册的用途
手册是本项目的**唯一事实来源（SSOT）**，唯一用途是帮助设计各个系统，切分成若干独立开发包，
分发给**互相看不到对方上下文的 AI agent** 各自实现。因此：
- 它可寻址、可裁剪、单一归属的事实库
- 每个被拆分的系统尽量遵循**可冷启动、可独立验收、可局部返工**

# 内容边界
允许写：接口签名与语义、数据结构与约束、依赖方向、状态机、伪代码、算法、时序
禁止写：框架 API 调用、类与继承设计、具体库选型与版本、性能优化手法

# 开发手册基础结构

## 第 0 层：AGENTS.md（仓库根目录）
**严格限量**，因为它是每个 agent 都必读的唯一全局文件。只放：
一句话项目定位 / 文档地图 / ID 命名规范 / 依赖方向铁律 / 开发红线 / Definition of Done。
不许放玩法内容。

## 术语表（独立于三层，全局共用）
一词一义，标注归属系统，禁止同义词并存。

## 设计层
1. 游戏概述
2. 非目标：明确不做什么
3. 核心循环
4. **系统划分**

## 协议层（契约层）
1. 技术栈（只到"选型约束与理由"，不到具体版本与用法）
2. 目录结构与命名规范
3. 数据表 schema 与存档格式
4. 模块边界与依赖方向
5. **全局事件/命令/查询总表**（系统之间唯一允许的交互方式）

## 执行层
1. 工作流（含讨论顺序、变更流程）
2. 验证方式
3. AI 协作约定
4. 决策记录（ADR）

# 系统划分要求
**划分标准：按状态所有权，不按 UI 页面或功能名词。**
每一份状态数据有且仅有一个系统是 owner，其他系统只能通过命令/事件间接影响它。
一个系统一次性整理、一次确认、统一落档，再进入下一个系统。

**参考的系统总表：
| 系统ID | 名称 | 一句话职责 | 所属层 | 拥有的状态 | 上游依赖 | 被谁依赖 | 规模(S/M/L) |

# 核心原则
1. 一次只讨论一个系统，不遗留待确认问题。
2. 不必顺从我的观点，做出独立分析和建议；我的方案有问题请直接指出。
3. 可以给出类似的游戏是如何设计的（2~3个），以向我提供思路。
5. 你可以并通过提问的方式与我交互以确认细节。
6. 可后置的实现细节，在构建对应模块时再展开。
