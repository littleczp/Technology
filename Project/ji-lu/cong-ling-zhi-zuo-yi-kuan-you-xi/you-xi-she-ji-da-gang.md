# 游戏设计大纲

> 使用2个主力 AI 模型，游戏设计如果出错会污染下游全部工作。好模型的价值在于反驳质量。
>
> 2个模型的输出做对比：
>
> * **两份非目标清单的差集，**&#x4E00;方想到而另一方没想到的，通常是我也没想清楚的边界。
> * **两句"一次迭代屏幕上有什么"，**&#x5982;果两边描述出的画面不一样，说明你的核心循环表述有歧义，这是必须当场修掉的。
> * **两份 DEFER 清单的差集，**&#x4E00;方认为需要原型验证、另一方认为可以现在定的问题。

{% code title="游戏设计大纲Prompt" overflow="wrap" %}
```md
我想使用AI从零制作一款游戏，
这个阶段只做顶层设计：确定做什么、不做什么。不涉及任何实现细节。

## 讨论顺序（必须严格遵守顺序，不许跳过）

### 0. 非目标
明确不做什么。至少 2 条。
这份清单在后续所有模块里都有否决权，任何提议如果撞上非目标，直接否决。

### 1. 游戏简介
一段话，指明玩家做什么、和什么游戏像。
这是约束不是总结。后面四个模块的产出如果无法被这段话概括，说明跑偏了。

### 2. 核心玩法（核心循环）
玩家反复做的那件事。它为什么有趣。
讨论结束时必须回答一句话："如果只做这个循环的一次完整迭代，屏幕上有什么？玩家能操作什么？"
这句话是下一阶段（垂直切片规划）的唯一输入，必须具体到能想象出画面。

### 2.5 参考实现盘点（核心玩法确认后立即做）
基于已确认的核心循环，联网搜索：
1. 有没有开源项目实现了类似的核心循环？列出 ≤ 5 个，每个给：
   仓库链接 / 语言引擎 / 许可证 / 最后更新时间 / 一句话相似点
2. 有没有相似但闭源的商业游戏？列出 2-3 个，说明它们怎么解决同一个问题。
3. 如果搜不到接近的，直接说没有。不要硬凑不相关的项目。

搜索关键词请用核心循环的机制描述，不要用我们游戏的标题或题材。
例如搜 "grid-based turn-based tactics open source"，
而不是搜游戏名或"策略游戏推荐"。

判断标准（按顺序看，不要只看 star 数）：
- 规模是否可读？超过 5 万行的参考价值急剧下降。
- 最后更新时间。三年没动的，依赖和引擎版本可能已不可用。
- 是不是教学示例？教学项目更好读，但数值没经过验证。

### 3. 内容与结构
关卡/进程如何组织。
内容从哪来（手工 / 程序生成 / 混合）。只讨论结构，不讨论具体关卡。

### 4. 叙事与世界观
只讨论：它是否服务于核心循环，以及需要多少。
如果结论是"叙事很薄"，那就明确写下来，这是个好结论，不是缺陷。

### 5. 美术风格
只讨论：风格方向、以及它的制作成本量级（我一个人 + AI 能不能做出来）。
不写风格指南。参考 2-3 个具体游戏即可。

## 讨论规则
- 一次只讨论一个模块。
- 每轮最多 3 个问题，只问"不回答就没法继续"的。
- 每个问题必须附带你的默认答案和一句话理由。由我来确认或者进行修改。
- 只有在手上有可玩原型才能判断的问题，标 [待游玩确认]，
  列进清单不要现在问。通常包括：手感、难度、节奏、数值。
- 举同类游戏时，先联网搜索核实，不要凭记忆。每个 ≤ 3 句。
  同时说明是否开源，有仓库就给链接。
  记不清或搜不到的，直接说"不确定"，不要编。
- 不必顺从我。方案有问题、范围过大、或属于非目标，直接说出来。

## 输出
确认所有模块后，输出一份《游戏设计大纲.md》(.md文件)。必须包含：
1. 非目标清单
2. 游戏简介
3. 核心循环，及那句"一次迭代屏幕上有什么"
4. [待游玩确认] 问题清单
5. 其余模块结论

未经我明确回复"确认"，不要输出文档。
```

```md
根据《游戏设计大纲.md》。参考项目（已clone）路径为：{{路径}}

这一步不写任何代码。目标是从参考实现里提取答案，减少后续猜测。

## 第一步之前：建立检索词表
我们用中文讨论，代码是英文的。grep 之前先做这件事，输出给我看。

1. 把每条中文 DEFER 问题映射到 2-4 个英文领域术语。
   用领域通行说法，不是字面翻译。
   例：跳跃手感 → coyote time, jump buffer, variable jump height, terminal velocity

2. 确认这个项目实际怎么命名。先读命名密度最高的地方：
   - 配置表 / 常量文件 / tuning 相关目录
   - 核心类型的字段定义
   - README 和 docs

3. 输出对照表：
   | 中文 DEFER 问题 | 通用英文术语 | 本项目实际命名 | 所在文件 |
   查不到的标"未找到"。

这张表确认后再开始 grep。

## 第一步：回答 DEFER 清单
【读法：定向 grep，不是通读】
逐条过清单。每条先想清楚用什么关键词，grep，再打开命中文件。
优先看配置表和常量定义，其次看使用这些值的代码。

给出：
- 具体数值或做法（文件路径 + 行号）
- 它为什么是这个值（能从注释 / commit / issue 看出就引，看不出就说看不出）
- 是否依赖参考项目的特有设计（如果是，对我们不适用，说明原因）

单条打开超过 5 个文件仍无结论 → 标"参考项目未明确回答"，跳过。
不要为了凑答案扩大搜索范围。

检索技巧：
- 数值类问题别搜概念，搜数字。配置表里 0.2 / 60 / 1000 附近就是答案，
  旁边的字段名会告诉你这个项目怎么称呼它。
- 命名风格不确定时先宽后窄：搜 cooldown 可同时命中
  dashCooldown / dash_cooldown / DASH_COOLDOWN。
- 找不到英文词时反向做：通读配置表字段名（通常几百行，读得完），
  再回来对照哪个字段对应哪条 DEFER。
- 注释和 commit message 里的自然语言往往比标识符更接近我们的说法。

## 第二步：核心循环的实现形态
【读法：从入口单向追踪，这一步允许多读一些】
1. 找到主循环入口（main / update / tick / _process 之类）。
2. 从入口出发，只跟随与我们那句"一次迭代屏幕上有什么"直接相关的调用链。
3. 一层跟一层，遇到无关分支立即停止，不要展开。
4. 追踪深度超过 4 层就停，再深的是它的内部实现。

用 ≤ 500 字描述：谁拥有状态、更新顺序、输入怎么进来。
预算：最多打开 15 个文件。到了就停，用已有信息作答。
超了说明核心循环过于分散、参考价值低，告诉我，我来决定要不要继续。

## 第三步：明确不参考什么
【基于前两步的发现来写，不需要额外读取】
列出建议不要学的部分，每条一句话理由。
常见来源：历史包袱、为多人/多平台付出的复杂度、撞上我们非目标的功能。

## 输出限制
- 输出一份《参考实现勘察报告.md》，总长 ≤ 4 页。
- 每个结论必须带文件路径。给不出路径的结论删掉。
- 不要生成"移植计划"或"改造方案"。这一步只做勘察。
- 不要建议 fork。我们要的是答案，不是它的代码库。

## 输出后立即自检（必须实际执行，不许口头确认）
对报告里每一个"文件路径 + 行号"引用：
1. 实际打开该文件的该行，把原始内容贴出来。
2. 如果对不上，删掉这条结论，标注"引用失效"。
3. 全部核验完，输出一行：核验 N 条，失效 M 条。

M > 0 的话，把失效的那几条重做一遍。
```
